🗡️ SLiCER (Safe Long-term Cloud Event Archival)

SLiCER is a cloud event archival engine designed to operate at the edge. It is capable of ingesting, encrypting, indexing, and synchronizing thousands of security logs per second, utilizing a multi-tier architecture that integrates local storage, mapped single or multi-cloud sync folders (e.g., Google Drive, Dropbox, Vawlt.io or academic alternative “Charon”, etc.), and AWS S3.

🚀 Key Features

  • High-Performance Ingestion: Asynchronous TCP engine capable of processing +5,000 EPS without Race Condition bottlenecks, utilizing an Atomic State Push pattern.

  • Format Agnostic: Native parsing support for CEF (e.g. ArcSight) and JSON logs, with dynamic device routing.

  • Shielded Storage: Data and indexes (Lucene/Bloom Filters) are packaged into .tar.xz and encrypted at rest via AES-256 GCM using an in-memory Master Password.

  • Multi-Cloud Synchronization (Egress-Drop): Automatic synchronization to mapped cloud folders (Google Drive, Dropbox, OneDrive, vawlt.io, etc.) and AWS S3, deleting raw local data to save space immediately after upload.

  • Distributed Real-Time Search: Search engine powered by Apache Lucene, with NDJSON Streaming support for instant UI rendering.

  • Graceful Shutdown: Shutdown interception ensures open blocks are securely closed and forces a synchronous upload to the cloud before the JVM dies, guaranteeing zero data loss.

📁 Directory Structure and Data Lifecycle

SLiCER's architecture is based on directories with strictly defined purposes. Understanding this structure is fundamental for operating the system and performing forensic analysis.

/storage
  ├── /ingest_cache           # 1. Hot Tier (Local Buffer and Active Indexes)
  │    └── /<device_name>
  │         ├── /data         # Recent raw logs (.tar.xz)
  │         └── /index        # Lucene Indexes + Bloom Filter
  ├── /tmp_charon             # 2. Warm Tier (Multi-Cloud / DropDir)
  │    └── /<device_name>
  ├── /exports                # 3. Investigation Tier (Decrypted Data)
  │    └── /<device_name>
/ledgers
  └── /<device_name>          # 4. Immutable Tier (Local Blockchain)

Folder Breakdown:

  1. /ingest_cache (Hot Tier): Where real-time magic happens. Incoming TCP events are buffered here. The engine rotates blocks based on time or size limits (e.g., 5MB or 15 mins). It has a strict retention policy: when limits are reached (e.g., 5GB), older blocks that have already been synced to the cloud are automatically pruned to free up space (Egress-Drop).

  2. /tmp_charon (Warm Tier): The integration point for multi-cloud storage. Although internally referenced as Charon, this is simply a local Drop Directory that can be mapped to any cloud sync service (like Google Drive, Dropbox) or a network NAS. Encrypted blocks (.enc) are copied here before AWS S3. SLiCER checks this folder for missing blocks before hitting S3, resulting in zero egress costs.

  3. /exports (Investigation Tier): When an analyst clicks "Decrypt and Export Block" in the Dashboard, SLiCER fetches the encrypted block, applies the in-memory AES-256 key, and extracts the raw, readable files here, ready for deep forensic analysis.

  4. /ledgers (Immutable Tier): The definitive system memory containing manifest_YYYY-MM.json files. Even when the /ingest_cache prunes old blocks to save space, the SHA-256 hash and block name remain in the Ledger. This tells the search engine: "This block exists, but you'll have to fetch it from the Warm or Cold tier."

🖥️ Threat Hunting Dashboard

The Web interface (accessible via http://localhost:7000) is not just a viewer, but an orchestrator for the decentralized storage.

1. Search Panel & Operation Modes

  • Device Selector: Focus searches on specific devices.

  • Simplified vs. Advanced Mode: Switch to advanced mode to write complex queries directly in Apache Lucene syntax (e.g., dvc:ids.snort AND status:404).

2. Event Tree-View Behavior

Results are delivered via NDJSON Streaming and rendered in real-time in separate tabs per device.

  • Cache vs. Cloud: Expanding a block in the UI triggers an event lookup. If the index/block is still in /ingest_cache (Hot Tier), display is instantaneous.

  • On-Demand Fetching: If the block was already pruned by the local retention policy (only existing in the Ledger), the UI alerts the user, requiring them to click the download button to retrieve encrypted data from the cloud (Warm/Cold Tier) before viewing raw logs.

3. "S3 Cost" Indicator

Cloud systems generate egress costs. SLiCER brings FinOps directly to the analyst:

  • During a search, if the system needs to download .tar.xz.enc files from AWS S3, the interface calculates the transferred megabytes.

  • A badge updates in the top right corner displaying something like ☁️ S3 Cost: ~$0.0945. If all data was retrieved from local cache or the mapped Multi-Cloud folder, the panel proudly displays ☁️ S3 Cost: Zero.

4. Selective Forensic Export

Unlike legacy systems that download entire daily backups, SLiCER is surgical:

  • "Download All Listed Blocks" Button: Clicking this button grabs only the specific block names that matched the current query and sends them to the backend.

  • Extraction: The backend retrieves only those specific files (from Local Disk, Drive/Charon, or S3), decrypts them, and places them in /exports/. This maximizes bandwidth savings and minimizes cloud costs.

🛠️ Installation and Execution

Prerequisites: Java 17+ and Maven 3.8+.

git clone https://github.com/username/slicer.git
cd slicer
mvn clean install

1. Starting SLiCER (Daemon): Run br.edu.utfpr.slicer.SlicerDaemon. The console will pause and prompt for the Master Password (required to derive the cryptographic key). Do not forget it!

2. Generating Traffic (Simulator): Ensure simulator.json is in the project root. Run the class br.edu.utfpr.slicer.tools.ThreatSimulator. It will inject simulated traffic (~5,300 EPS) from Firewalls, DBs, and Web Servers.

🧪 Simulating Searches Across Tiers (Local, Charon, S3)

SLiCER is smart about data retrieval. You can force the system to fetch logs from different storage tiers by intentionally deleting local files.

Warning: Turn off the ThreatSimulator before testing to prevent new blocks from confusing your analysis. NEVER delete files from /ledgers, as the system relies on them to track the generated block history.

Scenario 1: Hot Tier Search (Local Cache)

  1. Run the simulator for a few minutes and execute a query (e.g., dvc:ids.snort).

  2. The search will be nearly instantaneous, and the UI will display S3 Cost: Zero. The system found the indexes and raw data directly in /storage/ingest_cache/<device>.

Scenario 2: Warm Tier Search (Charon / Multi-Cloud DropDir)

Simulate that SLiCER pruned local data to save space (Egress-Drop), but the data still exists in your mapped sync folder (Google Drive, Dropbox, etc.).

  1. Navigate to /storage/ingest_cache/<device>/data and /storage/ingest_cache/<device>/index.

  2. Delete the closed block files and folders (.tar.xz archives).

  3. Go to the Web Dashboard and run the query again.

  4. The system consults the /ledgers, sees the blocks exist, attempts to fetch from ingest_cache (fails), and falls back to /storage/tmp_charon.

  5. The block is decrypted on demand. S3 Cost remains Zero since the transfer did not leave the local mapped drive.

Scenario 3: Cold Tier Search (AWS S3)

Simulate very old data that has been wiped from both the local cache and the local mapped cloud folder, surviving only in the AWS S3 bucket.

  1. Navigate to /storage/tmp_charon/<device> and delete everything.

  2. Ensure the /data and /index folders inside /ingest_cache are also empty (as in Scenario 2).

  3. Go to the Web Dashboard and run the query.

  4. SLiCER will try the cache (fail), try Charon (fail), and finally make a network call to AWS S3.

  5. The search will take slightly longer (download time), and the Web panel will update the ☁️ S3 Cost indicator with the estimated egress cost in USD.
